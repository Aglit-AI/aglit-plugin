# Safe default dev-history replay

Use after a rolling dev PR is rebase-merged, or when the default branch advances and the next PR has duplicate ancestry/conflicts. GitHub's rebase merge changes commit IDs: a shared dev branch can retain old commits whose changes already shipped. Fix history without rebuilding the product or hiding active work.

## Default: preserve the exact current product

Run on the authoritative checkout inside its common Git mutation mutex. Other Git mutations must use that same mutex; a second unrelated local lock is insufficient. The history-only path can preserve active source edits because it never writes working files or the real index. It is not permission to mutate another owner's content.

1. Verify repository, current dev branch, configured remote and actual default branch. Fetch both explicit refs. Record full old dev, remote dev and default SHAs, dev's tracked tree, and the real index tree. Stop for an unmerged index, local dev commits absent remotely, an existing Git operation or uncertain ownership. Do not stash, clean, reset or switch branches.
2. If default is already an ancestor of dev, no rewrite is needed. Otherwise classify patch-equivalent already-shipped commits with Git's cherry/patch-ID facilities. Preserve chronological pending non-equivalent commits. Do not infer equivalence from commit messages. Merge commits, partial cherry-picks or ambiguous dependencies need explicit inspection; never silently drop them.
3. Create a task-owned temporary Git index outside source and load the recorded default tree with `git read-tree`. Set `GIT_INDEX_FILE` only for replay operations; never point Git at the real index for these changes.
4. For each selected commit, obtain its exact binary-capable parent-to-commit patch and apply it to the temporary index, using three-way application when appropriate. Stop on conflict/unmerged entries. Write the temporary tree and a commit with the previous replayed commit as parent, retaining the original author/date and message. Use the authorized committer identity. Do not squash. Keep an old-to-new commit mapping.
5. Require the FINAL rebuilt tracked tree ID to equal the old dev tracked tree ID exactly. Equality is the decisive guard: already-shipped changes come from default, pending changes are replayed, and no tracked source/binary content changes. Also verify the real index tree and local dev ref still match the snapshots. Do not replace this guard with a successful patch application, a small diff or an assumption that Git skipped the right commits.
6. Recheck remote dev and default against their recorded SHAs immediately before publication. Preserve old dev under a unique archive tag. Publish the archive and rewritten dev atomically where supported, with force-with-lease bound to the exact old remote dev SHA. Never force-update default. Advance local dev with an expected-old-value ref update under the same mutex. Handle local/remote update failure explicitly: never roll back over another writer's new ref. Keep old/new SHAs and archive reachable for recovery; do not claim an atomic transaction across local and remote repositories.
7. Verify local/remote dev, unchanged tracked tree and shared index, and default ancestry after publication. If default advanced concurrently, report/reconcile the new state; do not claim a fresh clean base. Delete only the task-owned temporary index. Leave dirty, staged and untracked source plus other tasks' sessions intact.
8. Discover the OPEN PR for dev to the actual default branch. Create the next rolling PR when needed; never keep publishing evidence to the previously merged PR. Verify GitHub recalculates it as mergeable and that its diff contains only pending work. Update stale counts, commit mappings and history warnings. Keep draft status when real runtime/media proof remains incomplete, even if mergeability is clean.

The archive tag and exact lease are essential. A push lease only guards the remote ref it names; it does not serialize local writers or lock the default branch. Use both the common Git window and explicit snapshot checks. If the server cannot atomically archive and update dev, preserve the archive first, then lease-update dev; any partial outcome must be reported accurately.

## If the preservation guard fails

Leave published dev unchanged. A conflict or different final tree means this is not the safe history-only case. Preserve the attempted mapping/diagnostic outside source, record the concrete issue in the rolling PR, and use an actual content-integration window only when writers are quiescent and shared records establish ownership. Review both intended behaviors and run appropriate source/product checks. Do not silently choose one side, discard pending commits, commit others' dirty files, overwrite a moved ref, or use chat acknowledgement loops as a substitute for the existing coordination records.

Replaying safely is allowed by the user's authorized shared-dev workflow; it does not grant approval to merge the rolling batch, change app authorization, deploy production or mark a feature E2E-accepted.
